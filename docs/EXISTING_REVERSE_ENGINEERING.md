# Existing Broadcom reverse-engineering work

Checked **2026-10-15** using fresh web searches, first-party repositories, authors' technical writing and mailing-list messages. This is a research update to [the upstream baseline](DRIVER_BASELINE_AUDIT.md), not a driver-support claim. Target remains BCM63178, D11 **130.1**, AC-family PHY **51**, stock WLAN **17.10.121.37**. No device access, tracing, driver loading or firmware installation occurred. This original research note imports no external implementation, table, firmware or raw capture.

**The strongest new lead is the recent `aleferri/b43-ac-wip` project:** inspect its differential harness and kernel data-path structure before designing those layers from scratch. Its demonstrated target is substantially older: BCM4352/4360, core 42, AC-PHY 1 / radio 2069. The project supplies published implementation and logs, not evidence that its PHY tables or register contracts apply to our target. [Pinned project overview](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/README.md).

## The Quarkslab article supplied by the user

Quarkslab separates host drivers, ARM firmware and D11 microcode, explains firmware identification and ROM/RAM boundaries, and describes emulation checked against execution traces. Its useful lesson here is to identify the actual executing component and validate the path reached by a model before trusting its output. The article's FullMAC firmware workflow is not a core-130/PHY-51 hardware specification. Its CRC/signature observations apply to the studied firmware; they do not establish AX10 boot security or image acceptance. We should reuse that evidence discipline for our host-side `wl` analysis rather than assume a downloadable FullMAC image/protocol. [Quarkslab: Reverse-engineering Broadcom wireless chipsets](https://blog.quarkslab.com/reverse-engineering-broadcom-wireless-chipsets.html).

## Most actionable project: b43 AC-PHY work

The author reports 5-GHz association, WPA2 and traffic on a DSL-3580L with BCM4352/core 42/PHY 1. The pinned log contains hostapd association and completed RSN-handshake events at lines 48–50 and 108–110. That corroborates those reported events; it is neither our hardware test nor independent confirmation of every throughput/feature claim. The log's filename is dated October 11 while its embedded device timestamps say October 3; retain both when citing it. [Published bring-up log](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/bringup-log-2026-10-11-ht20-40.txt#L48).

A real implementation is present: `b43/phy_ac.c`, `b43/dma.c`, BCMA changes and separate unit/integration infrastructure. This improves the comparison material available beyond upstream's AC skeleton, while leaving PHY-51 radio initialization and calibration unresolved. [PHY implementation](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/b43/phy_ac.c), [DMA implementation](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/b43/dma.c).

The immediate reuse is **methodology and comparison structure**: an original trace schema with bank/core/space/address/width/value/barrier/delay, separate supplied read results, and strict event accounting. Existing components preserve selected operation, region and observation distinctions separately; a common schema, adapters and PHY/radio/table models remain to implement. The next harness should compose them and expose unresolved dependencies instead of filling them with successful stubs. This is a proposed application of the cited harness designs, not a claim those designs already support core 130.

## Accessor tracing and the ARM/Linux 4.1 gap

`wl-diag` uses MIPS32R1 entry detours, not kprobes, with return trampolines to capture read values. Its targets are kernel 3.4 / WLAN 7.14 and kernel 2.6.30 / WLAN 6.30. The documented operation classes distinguish PHY, radio, tables, object memory, template RAM, MAC and SI/PMU operations. It explicitly misses inlined `R_REG`/`W_REG`. [Accessor-tracer design](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/wl-diag/README.md).

The companion MMIO tracer changes mapping permissions and emulates MIPS faulting instructions to cover inline accesses. It documents refused instructions, timing distortion and assumptions about window moves/serialization. It is an intrusive live-kernel mechanism, **not** an ARMv7/Linux-4.1.52 tracing solution. [MMIO-tracer design and limits](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/wl-mmio-trap/README.md).

An optional parallel design task is offline: classify exact ARM call sites into hookable non-inlined accessors versus inline loads/stores, identify calling conventions/read-return boundaries, and quantify what a future tracer would miss. Kernel configuration, instruction rewriting, cache synchronization, concurrent execution and register-window ownership would all need independent review before any live mechanism. No live tracer was deployed in this pass. This design task does not displace current clock integration, PHY-register/TSSI/reset work or higher lifecycle composition.

## D11 microcode tooling

- **SEEMOO D11emu** is an actual emulator with stepping, breakpoints and state handling. Its stated range is core revisions 15–54, tested on 46/54. It can run standalone; hardware state extraction needs its companion patch for BCM43455c0. Use its architecture/test strategy as a reference, not an ISA or peripheral model for core 130. The associated paper is *Rolling the D11* (WiNTECH 2023). [Pinned D11emu README](https://github.com/seemoo-lab/d11-emu/blob/e5b362aea71d6f77e74212340f1e4144a942c6b3/README.md), [author debug-patch project](https://github.com/seemoo-lab/wintech23_nexmon_d11debug), [paper DOI](https://doi.org/10.1145/3615453.3616520).
- **b43-tools** supplies assembler/disassembler and firmware/initval utilities. Its historical ISA summary and brcm80211 initval decoder are useful format comparisons; neither proves modern object-memory fixups or core-130 instruction compatibility. Our observed effective-init behavior is broader than the old initval decoder. [Pinned assembler documentation](https://github.com/mbuesch/b43-tools/blob/36284a5731daae15d345c67248c3205e59f780a7/assembler/README), [old initval decoder](https://github.com/mbuesch/b43-tools/blob/36284a5731daae15d345c67248c3205e59f780a7/disassembler/brcm80211-ivaldump).
- **The AC project's b43-tools fork** adds an arch15 Python interpreter. Its README distinguishes validated decoding from uncertain/stubbed execution, and explicitly reports hardware-event wait loops it cannot resolve. Its reported tested blobs are core 42. This confidence tagging is useful for our future ucode analysis; byte decoding alone must not be called successful execution. [Pinned interpreter documentation](https://github.com/aleferri/b43-tools/blob/dd29f697bd87bdc962fd0048c6d2d01491053c7a/interpreter/README.md).
- **`test/d11sim`** compares final core state as well as operation streams, combining a host-side core model with that interpreter. It models **core 42** and explicitly supplies some handshake behavior. Treat it as a state-equivalence design reference; synthetic latches are not observations of an executing AX radio. [Pinned simulator design](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/test/d11sim/README.md).
- **Nexmon** is a firmware-patching framework, not a replacement Linux host driver. Its revision matrix is valuable because it separates chip/firmware targets rather than treating Broadcom as one ISA. No checked supported-target entry established BCM63178/core 130/PHY 51. [Pinned framework README](https://github.com/seemoo-lab/nexmon/blob/68720406f54ff16cad28fd3c51f2392aefad9fb7/README.md), [revision matrix](https://github.com/seemoo-lab/nexmon/blob/68720406f54ff16cad28fd3c51f2392aefad9fb7/REVINFO.md).

## Reuse and publication boundaries

The AC fork's top-level `LICENSE` is GPL-3.0, while examined files carry distinct notices: `b43/phy_ac.c` says GPL-2.0-or-later; `test/unit/wrap.c` and `test/integration/trace_out.c` say GPL-2.0. Review individual files and their dependencies before considering any code reuse; the repository badge alone is insufficient. This research imports no code. [Top-level license](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/LICENSE), [PHY notice](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/b43/phy_ac.c#L1), [harness notice](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/test/unit/wrap.c#L1), [integration notice](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/test/integration/trace_out.c#L1).

Its provenance file explicitly describes extracted radio/channel tables and stock-object analysis. Those tables, firmware, captures and board calibration are excluded from our publication/reuse plan. Link to the author and derive our own factual contracts from authorized exact-target evidence. [Author provenance](https://github.com/aleferri/b43-ac-wip/blob/01e132984f7f66f936f956deccf42ad77007e41a/PROVENANCE.md), [our publication policy](PUBLICATION_POLICY.md).

D11emu and Nexmon publish GPL-3.0 licenses; OpenBRCM publishes GPL-2.0-only; b43-tools components have their own COPYING/notices, including GPL-2.0 for the examined initval decoder and interpreter. Keep external tools and any future kernel/host implementation licensing decisions explicit. This note makes no blanket legal conclusion from a project's clean-room label. ## Concrete next actions

1. Design an **original offline differential harness** informed by the AC fork: bank-aware event records, independent read-result queues, table address context, explicit delays/barriers, missing/extra events and consumed-read-bit tests. Missing, exhausted and unconsumed read queues must fail explicitly; zero or write-echo replies require declared synthetic inputs or independently evidenced latch semantics, never implicit defaults. Preserve current versus secondary samples and pre/post-write observation freshness. Preserve current exact-target assembly traces as the oracle. Keep approximate alignment scores separate from exact regression tests.
2. Compare kernel data-path boundaries in the pinned AC fork and OpenBRCM with upstream mac80211/b43: DMA-map lifetime, RX completion versus TX-status ownership, interrupt masking/acknowledgment and stop-before-free. Convert useful questions into exact core-130 binary queries; do not transfer rev42 register offsets or descriptors by similarity.
3. Before using any D11 interpreter, establish core-130 encoding/operand widths and unsupported opcode/condition behavior from independent evidence. Start with synthetic instructions and private supplied artifacts; require explicit unsupported results. Keep emulated state changes distinct from readiness generated by a fake peripheral.
4. Write a trace-coverage design for the ARMv7 4.1.52 stock build. Determine which accessor boundaries survive inlining and which MMIO operations would need different instrumentation. Do not deploy a tracer as part of this research task.
5. Keep PHY-51 reset/channel/radio/calibration contracts, board power/window ownership, and HE/data-path integration as open target-specific work. Use the older projects to reduce method/design work, not to waive those requirements.

These are proposed next implementation/research steps, not actions performed by this note.
